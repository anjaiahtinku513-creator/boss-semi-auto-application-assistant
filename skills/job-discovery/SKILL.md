# 岗位发现与匹配

## 目标

把用户的真实履历和求职约束转换为可执行的搜索条件，并生成可追溯的岗位候选清单。先执行确定性硬筛选，再进行评分；评分不得推翻硬性淘汰结果。

按用户本次范围执行：搜索任务建立候选池；单份 JD 评估直接使用该 JD 与相关履历；局部复核只重查受影响的筛选项和结论。已有画像和已确认事实可以复用，不为单岗判断重新搜索、重复采集全部履历或强制生成完整候选池。市场、岗位和用户事实分别标识，不能跨岗位混用证据。

## 输入

优先收集以下信息；已有信息不要重复询问：

- 通用简历或事实清单，包括技能、项目、年限、学历和可证明成果。
- 主目标岗位、3-5 个同义岗位、最多 2 个相邻岗位。
- 城市、通勤上限、远程或混合办公偏好。
- 薪资下限与目标区间，注明税前月薪、年薪及月数口径。
- 必须满足、可妥协和明确排除的条件。
- 岗位来源：当前可见页面、用户粘贴的 JD、用户提供的导出文件或公开网页。

若缺少的信息会改变硬筛选结论，只提出最少量的澄清问题。若用户要求先试跑，使用明确标注的临时假设，不把假设写成用户事实。

## 工作流

1. 建立搜索画像
   - 将条件分为 `hard_requirements`、`preferences` 和 `exclusions`。
   - 将履历拆为“已验证事实”和“未知信息”；未知不得当作已具备。
   - 明确搜索时间窗、岗位数量上限和停止条件。
2. 获取岗位
   - 默认处理用户粘贴内容、导出文件或当前浏览器中可见的页面信息。
   - 仅在用户明确要求浏览器协助时操作当前已登录页面，并保持低频、有限范围。
   - 保存来源链接、采集时间和能支持判断的 JD 原文片段。
3. 标准化与去重
   - 统一职位名、公司名、城市、薪资、经验、学历、发布日期和 HR 活跃信息。
   - 按链接或职位 ID 去重，再按“公司 + 职位 + 城市 + JD 指纹”去重。
4. 先做硬筛选
   - 开始判断前读取 [筛选与评分规则](references/search-and-scoring.md)。
   - 每个淘汰项必须给出触发规则和来源证据，不得只写“不匹配”。
5. 再做评分
   - 仅对通过硬筛选或标记为 `needs_review` 的岗位评分。
   - 分数必须附维度明细、证据覆盖率和不确定项。
6. 输出候选清单
   - 需要结构化记录或跨步骤交接时读取 [岗位记录规范](references/job-record-schema.md)。
   - 默认先展示高价值候选，不为低分岗位生成简历材料。

## 浏览器边界

- 不索取、记录或导出密码、Cookie、令牌及其他登录凭据。
- 不绕过验证码、登录限制、访问控制、频率限制或平台风控。
- 不调用未公开接口，不做隐藏 API 逆向，不注入反检测代码。
- 不点击“立即沟通”“投递”“发送”等会产生外部影响的按钮。
- 页面结构变化、验证码、登录失效或平台提示限制时立即停止并报告。
- 遵守目标网站服务条款和适用规则；无法确认允许性时退回手动复制 JD 模式。

## 输出要求

以下是完整候选清单的默认交付；单岗或局部复核只展示相关结论、证据、缺口和下一步，不机械补齐无关栏目：

1. 本次搜索画像和临时假设。
2. 已扫描、去重、硬淘汰、待复核和推荐数量。
3. 按分数排序的候选表。
4. 每个推荐岗位的匹配证据、主要缺口和建议动作。
5. 淘汰记录及明确原因。
6. 下一步交接包：选中岗位的完整 JD、来源、评分和待确认项。

用户选定岗位后，交给 `$resume-application-pack` 生成材料；本 Skill 自身不生成最终投递简历、不发送消息。
