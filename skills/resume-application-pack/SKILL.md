# 岗位定制简历包

## 目标

在不改变事实的前提下，让简历表达与目标 JD 更直接对应，并把每一处实质性改动追溯到用户提供的证据。输出是待用户审核的草稿，不是已授权投递的成品。

完整材料包按下列流程交付；用户只要求改一段简历或一句话术时，复用已有事实，只修改该部分并给出必要核验，不重建整套材料、不擅自导出文件。用户明确的长度、语言和输出形式优先于默认模板，事实边界和主简历只读要求保持不变。

## 必需输入

- 目标岗位的完整 JD、公司名、职位名和来源。
- 通用简历原文或文件。
- 可选的事实清单，例如 `facts.yaml`、项目材料、作品集或用户本轮确认的信息。
- 用户对长度、语言、版式和文件格式的要求。

完整定制版缺少完整 JD 或通用简历时，不直接生成。局部改写可使用与该段有关的原文、岗位要求和已确认事实；若不足以判断事实或岗位含义，只询问当前受阻部分所需的信息，不把缺少无关材料视为全部停工的理由。

## 工作流

1. 锁定源文件
   - 将通用简历视为只读主版本，绝不原地覆盖。
   - 若用户只要求“在对话中生成文本”，不得创建、修改或导出简历文件。
2. 建立事实台账
   - 先读取 [证据与改写规则](references/evidence-and-tailoring.md)。
   - 把信息标记为 `verified`、`derived`、`pending_confirmation` 或 `conflict`。
   - JD 只能说明招聘方需求，不能证明用户具备某项能力。
3. 解析 JD
   - 分离硬要求、核心职责、加分项、业务场景和关键词。
   - 建立“JD 要求 -> 用户证据 -> 可用表达 -> 缺口”的映射。
4. 生成定制简历草稿
   - 优先重排、压缩、澄清和替换为真实同义表达。
   - 强化最相关的 3-5 条证据，弱化与岗位无关的内容，但不篡改时间线。
   - 只使用用户已经真实掌握且有来源的 JD 关键词。
5. 生成打招呼话术
   - 用 2 个最强匹配点说明为什么值得继续沟通。
   - 保持简短、自然、针对该岗位；避免“非常荣幸”“贵司前景广阔”等空泛套话。
   - 不承诺未确认的入职时间、薪资、出差、加班或技能水平。
6. 做事实核验
   - 逐条检查新增、强化、量化和关键词替换。
   - 含 `pending_confirmation` 或 `conflict` 的内容不得进入最终草稿；放入待确认清单。
7. 交付并等待审核
   - 需要落盘时，按 [申请材料包格式](references/application-pack-format.md) 创建独立岗位目录。
   - 先展示关键改动、风险和待确认项，再给出完整草稿。
   - 状态只能到 `ready_for_user_review`；用户明确批准当前版本后才可标记 `user_approved`。

## 不可违反的规则

- 不新增不存在的公司、岗位、项目、技能、证书、学历、职责、管理范围或成果。
- 不扩大参与程度，例如把“协助”改成“负责”、把团队成果写成个人独立成果。
- 不修改任职时间以满足年限，不拼接不同项目制造新经历。
- 不推算或美化金额、增长率、排名、人数、预算和效率数据。
- 不用不可核实的软技能自评替代证据。
- 不为了 ATS 关键词覆盖而堆砌用户不会的工具或术语。
- 不自动上传、投递、点击沟通或发送话术；这些动作始终由用户确认并执行。

## 输出

每个完整岗位材料包默认输出；局部修订按用户要求交付对应部分：

1. 定制简历草稿。
2. 一条推荐打招呼话术和一条更短备选。
3. 修改日志：修改前、修改后、对应 JD、事实来源和原因。
4. 事实核验：通过项、待确认项、冲突项和删除项。
5. 材料状态与下一步人工动作。

若硬要求明显不满足，先说明风险并建议返回 `$job-discovery` 复核，不通过措辞包装掩盖实质缺口。
